# Accessibility lens (WCAG 2.2 AA)

Target: WCAG 2.2 Level A and AA, the current W3C Recommendation (12 December 2024). WCAG 3.0 is a working draft and is not a conformance target; do not cite it. When **Accessibility target** is set, it wins. 2.2 removed 4.1.1 Parsing; do not report it. AAA criteria are optional: report them as `Low` only when cheap, and label them AAA.

Check the source first, then confirm runtime behaviour when a browser or an automated test is available (`references/browser-verification.md` next to this SKILL.md). Mark anything that needs a person with a screen reader `[VERIFY]`. Cite the success criterion (SC) number in each finding.

## Semantics and names

- Interactive elements are real controls (`button`, `a href`, `input`, `dialog`), not `div` with a click handler. Custom widgets follow the ARIA pattern for their role. No ARIA is better than wrong ARIA (SC 4.1.2).
- Every control has an accessible name: visible text, an `aria-label` when the text is an icon, or a programmatic label for form fields (SC 1.3.1, 4.1.2). The accessible name contains the visible label text (SC 2.5.3).
- Images have a meaningful `alt`, or `alt=""` when decorative (SC 1.1.1). Do not use images of text where text can do the job (SC 1.4.5).
- `id` values are unique in the rendered page. Items rendered in a list must not share a static `id`, because labels and `aria-describedby` then point at the wrong element.
- Headings describe their sections and are in a logical order (SC 1.3.1, 2.4.6). `main` appears once. Several `nav` or other repeated landmarks have distinct labels. A way to skip repeated blocks exists (SC 2.4.1).
- Each page or view has a descriptive title (SC 2.4.2). The page language is set (SC 3.1.1). Link text makes sense in context (SC 2.4.4).
- Input purpose is declared with `autocomplete` on fields that collect personal data (SC 1.3.5).

## Keyboard and focus

- Every interactive element is reachable by Tab, operable with Enter or Space, and not trapped (SC 2.1.1, 2.1.2). Character-key shortcuts can be turned off or remapped, or only work when the control has focus (SC 2.1.4).
- Focus order follows the meaning of the content (SC 2.4.3) and focus is visible in every state (SC 2.4.7).
- A focused element is not entirely hidden by sticky headers, footers, cookie banners, or other overlays (SC 2.4.11, new in 2.2). Check by tabbing through the page with such content present.
- Dialogs and popovers move focus in on open, keep it inside while open, close on Escape, and return focus to the trigger (SC 2.4.3).
- Removed or re-rendered content does not drop focus to the document body.
- Focusing or changing a control does not trigger an unexpected change of context, such as a navigation or form submit (SC 3.2.1, 3.2.2).
- Content that appears on hover or focus can be dismissed without moving the pointer, can be hovered, and stays visible until dismissed (SC 1.4.13).

## Pointer and touch

- Dragging has a single-pointer alternative, such as buttons or a tap-to-place flow (SC 2.5.7, new in 2.2).
- Pointer targets are at least 24x24 CSS pixels, or have enough spacing, or have an equivalent control, or are inline in text, or are a user-agent control, or the specific size is essential (SC 2.5.8, new in 2.2).
- Multi-point and path-based gestures (pinch, swipe) have a single-pointer alternative (SC 2.5.1). Actions fire on release, and can be aborted or undone (SC 2.5.2).
- Content works in both portrait and landscape unless one orientation is essential (SC 1.3.4).

## Forms and errors

- Each field has a visible label. Placeholder text is not the only label (SC 1.3.1, 3.3.2).
- Errors are identified in text and tied to their field (`aria-describedby` or equivalent), and the first error receives focus on submit (SC 3.3.1). Correction suggestions are given when known (SC 3.3.3).
- Required fields are marked in text and programmatically (SC 3.3.2).
- Submissions that are legal, financial, or that change or delete user data are reversible, checked, or confirmed (SC 3.3.4).
- Information the user already gave in the same process is auto-filled or offered for selection, not asked for again (SC 3.3.7, new in 2.2).
- Sign-in does not require a cognitive function test (remembering a password, solving a puzzle) without an alternative. Allow paste and password managers, and do not block `autocomplete` (SC 3.3.8, new in 2.2).
- Help links, contact details, or chat that repeat across pages appear in the same relative order (SC 3.2.6, new in 2.2).

## Dynamic content and time

- State changes that swap content are announced through a live region, or focus moves to the new content (SC 4.1.3).
- Loading indicators are announced or given accessible text.
- Time limits can be turned off, adjusted, or extended (SC 2.2.1). Moving, blinking, or auto-updating content lasting over 5 seconds can be paused, stopped, or hidden (SC 2.2.2). Nothing flashes more than three times per second (SC 2.3.1).
- Video and audio have captions and a transcript or audio description where the content needs them (SC 1.2.x). Audio that plays automatically for over 3 seconds can be stopped (SC 1.4.2).

## Visual

- Text contrast is at least 4.5:1, large text 3:1, UI components and focus indicators 3:1 (SC 1.4.3, 1.4.11). Check token values, not rendered screenshots alone.
- Content works at 200% text zoom and at 320 CSS pixels width without horizontal scrolling or loss of content, except parts that need a two-dimensional layout such as a table, map, or diagram (SC 1.4.4, 1.4.10). Content survives user text-spacing overrides without clipping (SC 1.4.12).
- Colour is not the only way to convey state (SC 1.4.1).
- Honour `prefers-reduced-motion` for non-essential animation. This is best practice, not an AA requirement: SC 2.3.3 is AAA, and SC 2.2.2 requires only a pause control for long auto-moving content.
- AAA, optional: focus indicator size and contrast (SC 2.4.13), focus never obscured at all (SC 2.4.12), contrast 7:1 (SC 1.4.6).

## Evidence

Automated checks (axe in tests, or the project's a11y tooling) find only part of this, and cannot judge accessible-name quality, focus order, or whether a live region announces the right text. Report what the automated check covered and what it did not. A finding with no source line or runtime observation is `[VERIFY]`.
